1. 概要

PDF / Markdown / テキストの資料を取り込み、チャットで質問すると資料の該当箇所（ファイル名・ページ・抜粋）を根拠として示しながら回答するQ&Aアプリです。
v2 「文章を書くのは Claude、判断するのは Jev」という役割分担にします。検索したチャンクが質問に関係あるかの判定と、生成した回答が根拠に裏付けられているかの検証を、判断特化モデル Jev が高速・低コストで行います。
関係するチャンクが無ければ質問を言い換えて1回だけ再検索し、それでも無ければ「資料からは分かりません」と正直に答えます。LangChain / LangGraph の最小構成で、Docker で一発起動できるポートフォリオ用デモとして半日規模で仕上げます。

できること資料の一括取り込み／UIからのアップロード／根拠つき回答／回答の裏付け検証／「分からない」の明示
作らないもの認証・ユーザー管理／DBの作り込み／管理画面／会話履歴の永続化
差し替え可能な点docs/ の資料を入れ替えるだけで、社内マニュアル・規程集・製品資料のQ&Aになる。Jev キーが無くても Claude だけで動く
Jev とは：TypeSafe AI が2026年9月に公開した「判断特化」モデル。文章を生成せず、判定対象のデータ（state）と型つきの質問を渡すと、Noul（真である確率 0〜1）／Choice（選択）／Score（採点）で答えを返す。 入力 $0.042/100万トークン・出力無料、応答は数百ミリ秒。文章を作らないので「捏造」は起きないが、判断自体が間違う可能性はあるため、本設計では閾値とフォールバックを前提にする。

v2 judge.py のインターフェース（Jev / Claude を差し替え可能にする）

class Judge(Protocol):
    def grade(self, question: str, chunks: list[str]) -> list[float]:
        """各チャンクが質問に答える情報を含む確率（0〜1）を返す"""
    def verify(self, question: str, answer: str, chunks: list[str]) -> float:
        """回答が根拠チャンクに裏付けられている確率（0〜1）を返す"""

# JevJudge   : typesafe-sdk の system_one() に Noul 質問を投げる（grade は k 問を1リクエストに同梱）
# ClaudeJudge: 同じ質問を Claude の構造化出力で答えさせる（TYPESAFE_API_KEY 未設定時）
# get_judge(): 環境変数を見てどちらかを返す。LangGraph のノードは Judge だけに依存する
なぜ確率で受け取るか：Jev の Noul は Yes/No ではなく確率を返すので、閾値を環境変数で調整できます。日本語での精度は公式も「英語より劣る」と明記しているため、sample_docs で実測して閾値を決め、画面にも確率を出して挙動を目で確認できるようにします。

②SSEで逐次表示		 ① 非対応 verify を通してから返す設計なので、逐次表示とは相性が悪い点もある。拡張案としてREADMEに記載

技術リスクと対策

リスク影響対策
verify の判定指示が厳しすぎると、正しい一覧回答を弾く（実測: 旧指示で 0.63〜0.73 と閾値付近）「断定できません」が増え、使い物にならない実資料で較正済み（v2.1）。「網羅性は問わない」「記載なしの断り・表記揺れの注記は裏付け不要」と指示に明記し、正しい一覧回答 0.90 / 捏造回答 0.06 に分離。指示は prompts.py に集約し再較正しやすくする
Jev の日本語精度（公式が「英語より劣る」と明記）関係あるチャンクを落とす／無関係を通す。verify が正しい回答を弾く確率で受け取り閾値を環境変数化。sample_docs で実測して初期値を決める。grade を外しても rewrite の再検索が救済。判定値を画面に出して挙動を可視化
Jev が2026年9月公開の新サービス（API変更・障害の可能性）デモが動かなくなる呼び出しを judge.py に閉じ込め、Jev 側のエラー時は 自動で ClaudeJudge にフォールバックし、steps にその旨を記録。テストはモックなので外部依存なし
「Jev はハルシネーションしない」という表現の誤解READMEの記述が過大になるREADMEでは「文章を生成しないので捏造は起きないが、判断は間違い得る。だから閾値とフォールバックを設ける」と正確に書く
Dockerイメージが大きくなる（ONNXランタイム＋Chroma＋埋め込みモデル）初回ビルド・起動が遅いuv のキャッシュ活用、マルチステージビルド、埋め込みモデルはボリュームにキャッシュして2回目以降は即起動
日本語資料の検索精度（埋め込みモデルの日本語性能）関係あるチャンクを取り逃す多言語対応モデルを選定し、実装時に sample_docs で日本語クエリを確認。rewrite ノードが取り逃しを一部救済
OCR 資料の表記揺れ・表の分断（実資料で発生）固有名詞で検索が外れる／表の見出しと行が別チャンクになり一覧が欠けるBM25 の照合で濁点・半濁点を無視。取得チャンクを同じページ全体に展開（EXPAND_TO_PAGE）。実測で 12 件中 7 → 12 件に改善（v2.1）
PDFがスキャン画像（文字が取れない）取り込んでも空チャンクv1はテキスト抽出のみ対応。空のページはスキップし、取り込み結果に警告を出す。OCRは拡張案
ローカル環境が Python 3.14（新しすぎて一部ライブラリ未対応の可能性）ローカル実行でエラーDocker（Python 3.12）を正とし、ローカルも uv で 3.12 を使う
